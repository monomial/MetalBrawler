## Problem Statement

Build a top-down roguelike brawler inspired by TMNT: Splintered Fate, targeting macOS, iOS, and tvOS. The developer previously built a Sky Force-style vertical scroller using Metal + ObjC/ObjC++ and wants to apply that Metal knowledge to a fundamentally different genre. The game should be something friends and family (casual gamers) pick up and say "I can't believe you made this."

This is a learning project with craft as the primary motivation — specifically engineering the sensation of impact (hitboxes, knockback, hit-stop frames, screen shake, haptics). The roguelike structure is the container; combat feel is the product.

## What Makes This Cool

Combat that feels physical on Apple Silicon. Three things combine:
1. **Hit-stop frames** — global time-scale freeze (2–4 frames) on contact. Punching feels heavy.
2. **Screen shake** — exponential decay offset on the camera matrix. Easy to add, hard to forget once present.
3. **Core Haptics (iOS/tvOS)** — `CHHapticEngine` patterns tuned per attack type (jab = light tap, heavy = thud+rumble, parry = double-pulse). Almost no indie games use haptics intentionally. This is a free differentiator on Apple hardware.

The roguelike loop (rooms, runs, permadeath, unlocks) is what keeps players coming back. But the "whoa" from casual players comes from the first punch landing with all three of the above active.

## Constraints

- Apple ecosystem only: macOS + iOS + tvOS
- Metal + ObjC/ObjC++ — no game engine, no SpriteKit. Metal learning is part of the goal.
- Code-first, agent-friendly: minimal visual editor dependence. Text files, data files, code.
- Input must handle three modes from day one: keyboard/mouse (macOS), touch (iOS), gamepad/remote (tvOS). `InputState` struct: `{ float moveX; float moveY; bool attack; bool dodge; bool pause; }` — all values normalized before game logic sees them.
- Objective-C/Objective-C++ with C++ allowed for ECS internals, simulation, and rendering
- First ship = one character, one enemy type, one room, one run. No meta-progression until the core loop is fun.

## Premises

1. **Metal (not SpriteKit)** — Metal learning is part of the goal. Custom shaders, post-processing (radial blur on hit), and particle effects at scale all require raw Metal.
2. **ECS architecture** — roguelikes with items, status effects, and enemy variants hit OOP inheritance walls. Flat C struct components + system functions avoid this.
3. **Combat feel is the first playable milestone** — hitboxes, knockback, hit-stop, screen shake, and haptics before any roguelike structure.
4. **Input abstraction from day one** — keyboard/touch/gamepad all resolve to a single `InputState` struct before game logic sees them. Normalizing in `Platform/InputEvent` (pattern from Shooter) means no per-platform branches in game code.
5. **First ship = one character, one enemy, one room, one run** — validate the core loop before adding meta-progression, unlocks, or multiple characters.

## Approaches Considered

### Approach A: ECS-first, feel layer second (Chosen)
Build the full ECS skeleton — component types, system loop, event bus — before implementing combat feel. Architecture is correct from day one; feel systems slot in once the structure is proven.

Effort: L (weeks before first satisfying hit)
Risk: Medium
Pros:
- No refactoring debt — the architecture is right before any game logic is written
- ECS makes adding enemies, items, and status effects trivial once wired
- `HitStopSystem` and `ScreenShakeSystem` are natural ECS systems, not hacks
Cons:
- Delayed gratification — several days before hitting an enemy feels satisfying
- Risk of over-engineering the ECS before validating the combat premise
Reuses: Metal triple-buffer pattern, input normalization, perspective camera from Shooter

### Approach B: Feel-first spike, refactor to ECS
Prototype combat feel in one weekend, validate it, then rebuild as ECS.

Effort: M (playable in ~1 weekend, ECS in ~2-3 weeks)
Risk: Low
Pros: Fastest path to "whoa" validation
Cons: Throwaway code, two codebases in sequence

### Approach C: Flat C structs + ECS-compatible from day one
Use flat C struct arrays as components from day one (no OOP entity classes). Naturally scales into ECS without upfront framework overhead.

Effort: M (same weekend timeline as B)
Risk: Low
Pros: No throwaway code, ECS-ready from start, feel validation in weekend 1
Cons: Requires discipline to keep systems separate

## Recommended Approach

Approach A (chosen by developer) — ECS skeleton before feel layer. Note: the component representation is flat C structs throughout (consistent with Approach C's mechanics), but the sequencing follows Approach A: build `World`, systems, and event bus first, then layer in combat feel. The accelerated first milestone ("one character, one enemy, one attack, one death") keeps the delayed-gratification cost bounded. Once that gate passes, the architecture is proven and feel systems slot in naturally.

**Recommended ECS layers (build in order):**
1. `World` — entity ID allocator, component storage (typed arrays), system registry
2. `TransformComponent`, `VelocityComponent`, `HitboxComponent` — flat C structs
3. `PhysicsSystem` — AABB overlap, no rotations needed for brawler
4. `RenderSystem` — Metal sprite batcher, pulls from TransformComponent
5. `InputSystem` — normalizes to `InputState`, feeds `VelocityComponent` updates
6. `CombatSystem` — attack state machine, hitbox activation windows, damage events
7. `HitStopSystem` — global time-scale multiplier, freeze N frames on contact
8. `ScreenShakeSystem` — camera offset, exponential decay
9. `HapticsSystem` (iOS/tvOS only) — `CHHapticEngine` patterns per attack type

## Decisions Made

1. **ECS framework: hand-rolled C++ World class.** `std::vector<ComponentType>` for all component storage — cache-friendly, safe, resizable. ObjC game loop calls C++ via `.mm` bridge file. ~300 lines total; EnTT available as fallback if the hand-rolled version proves inadequate.

2. **Component memory layout: Array of Structs (AoS) for V1.** SoA gives better cache performance at scale, but AoS is simpler to reason about and debug. Profile before switching.

3. **Deferred entity lifecycle.** `World.defer_create()` / `World.defer_destroy()` buffer all entity changes; `World` flushes after all systems complete each frame. Prevents mid-frame corruption when CombatSystem kills an enemy and spawns a loot drop in the same tick.

4. **Dual deltaTime: `World.update(physicalDt, gameDt)`.** `HitStopSystem` scales `gameDt` to zero for N frames on contact; the render loop keeps running. AudioSystem receives `physicalDt` (never freezes); all logic systems receive `gameDt` (freezes during hit-stop). This makes HitStop zero-cost for any new system added later.

5. **Renderer: 3D models + perspective camera (scope change from original 2D assumption).** Camera pitched ~55° from horizontal, matching TMNT:SF's visual depth. Requires: rigged 3D character models, skeletal animation system, GPU skinning pass in MSL, perspective projection matrix. Sprite batcher from Shooter does NOT apply; this is a mesh renderer.

6. **Camera: player-following with perspective projection** pitched ~55°. `ScreenShakeSystem` applies exponential-decay offset to the camera's world-space position before computing the view matrix. One uniform buffer upload per frame.

7. **Event bus: struct-based ring buffer.** 256 slots per frame; events are plain C structs (no heap allocation). Overflow policy: assert in debug builds (catches bugs immediately), silent drop + increment overflow counter in release builds (prevents crash; logs allow field diagnosis). One XCTest case validates slot 257 drops cleanly.

8. **System execution order (per frame):**
```
Frame N execution:                        deltaTime used:
  1. InputSystem      — read InputState   (physical)
  2. PhysicsSystem    — AABB, integrate   (game)
  3. CombatSystem     — hitboxes, damage  (game)
  4. HitStopSystem    — scale gameDt      (physical — sets game scale)
  5. AnimationSystem  — bone matrices     (game — already scaled)
  6. AudioSystem      — sound triggers    (physical — never freezes)
  7. HapticsSystem    — CHHapticEngine    (physical)
  8. ScreenShakeSystem — camera offset    (physical)
  9. World flush      — deferred create/destroy
  10. RenderSystem    — mesh draw, present (physical)
```

9. **Physics tick rate: 120Hz fixed timestep, 60Hz render with interpolation.** Physics ticks at 8.33ms; render at 16.67ms. Prevents hitbox tunneling and halves worst-case input lag. Same pattern as Shooter (already understood), tick rate now explicit.

10. **Skeletal animation system:** `AnimationComponent` holds: clip array, current clip ID, clip time accumulator, bone matrix array (`float4x4[MAX_BONES]`). `AnimationSystem` samples the current clip at `gameDt`-accumulated time, outputs bone matrices. GPU skinning pass in MSL reads bone matrices from a uniform buffer. Clip format and bone hierarchy spec required before Step 8 of implementation (see TODOs).

11. **Audio:** `AVAudioEngine` for low-latency sound effects. **Initialize at app startup, not on first sound** — `AVAudioEngine.start()` has a ~50-100ms startup cost. Lazy init causes an audible hitch on the first hit. Required for feel milestone — hit-stop without audio is half the feedback.

12. **tvOS input specifics:** `InputState` maps to logical actions, not physical buttons. Siri Remote: touchpad delivers **swipe deltas** (not absolute position) — `InputSystem` must apply dead-zone filtering and an acceleration curve before writing to `moveX/moveY`. This is a platform-specific code path the abstraction hides but does not resolve. MFi/Xbox controller maps analog stick → same logical field. `CHHapticEngine` on tvOS requires Siri Remote 2nd gen (tvOS 14+) — guard with `CHHapticDeviceCapability.supportsHaptics`.

13. **Character art:** Original characters required (can't ship TMNT IP). Placeholder geometry (colored rectangles) for ECS milestone; rigged 3D models with walk/attack/hurt/death animations for feel milestone. Art pipeline decision is a required TODO before feel milestone begins (see TODOs).

## Ground Hazard System Design (floor-is-lava)

Inspired by TMNT: Splintered Fate boss mechanic: boss spawns one or more "lava snakes" that crawl along the ground in looping patterns. Player takes damage on contact.

### ECS mapping

**New components:**

`PathComponent` — defines the route a hazard entity follows. The key design question (open — see below) is how the path is stored and interpolated.

```
struct PathComponent {
    // Option A: inline waypoints (simple, fixed max)
    simd_float2 points[MAX_PATH_POINTS]; // world-space positions on the ground
    int         numPoints;
    int         currentTarget;  // index of next waypoint
    float       speed;          // units/sec
    bool        loop;           // wrap back to point[0] on completion
    float       t;              // 0..1 interpolation between currentTarget-1 and currentTarget
};
```

`HazardComponent` — marks entity as a passive area-damage source:
```
struct HazardComponent {
    float damageRadius;   // collision radius in world units
    int   damagePerHit;
};
```

`DamageCooldownComponent` — on the **player** entity. Prevents 120 hits/sec from a hazard overlap.
```
struct DamageCooldownComponent {
    float remaining; // seconds until player can take damage again
};
```

**New systems (frame order insertion):**

```
1.   InputSystem
1.5  EnemyAISystem
1.7  PatternSystem    ← advances PathComponent.t, writes PositionComponent directly
2.   PhysicsSystem    ← skips hazard entities (no VelocityComponent)
3.   CombatSystem
3.5  HazardSystem     ← player-hazard overlap → damage with cooldown check
4.   HitStop ...
```

`PatternSystem` — each tick, advances `t` toward the next waypoint at `speed`. When `t` reaches 1.0, advances `currentTarget` (wraps if `loop`). Writes `PositionComponent` from linear interpolation between waypoints. No `VelocityComponent` on these entities — PhysicsSystem skips them.

`HazardSystem` — for each hazard entity, checks distance to player. If within `damageRadius` and player's `DamageCooldownComponent.remaining <= 0`, deals damage and resets cooldown. Decrements all active cooldowns each tick.

**Boss ownership:** Boss entity calls `defer_create()` to spawn snake entities on phase transition, `defer_destroy()` when boss dies. Snake entities carry a back-reference to the boss entity ID if needed for lifetime coupling.

**Multiple segments:** A snake that appears as a long body is N entities spaced evenly along the same path (each with a different starting `t` offset — e.g., 3 segments at t=0.0, t=0.33, t=0.66). All follow the same waypoints; only `t` and `currentTarget` differ.

### Open questions (resolve before implementing)

1. **Path interpolation:** Linear between waypoints is simple but looks robotic at corners. Catmull-Rom spline through the waypoints gives smooth curves with no extra authoring effort. Decision affects `PatternSystem` complexity. **Recommendation: linear for V1, add spline if it looks bad.**

2. **Path storage:** Inline waypoints in the component (simple, 16-point max) vs. path data referenced by ID from a shared asset table (more flexible, enables multiple snakes sharing one path). **Recommendation: inline for V1 since the boss has one or two distinct patterns.**

3. **Waypoint authoring:** Hardcoded in the boss spawn logic vs. loaded from a data file (JSON). JSON is more tunable without recompiling. **Recommendation: hardcode V1, migrate to JSON when tuning begins.**

4. **Snake visual representation:** Single entity with large collision radius vs. multiple segment entities for a "body" effect. The segment approach looks better but multiplies entity count. **Recommendation: single entity with radius for ECS milestone; add segments for feel milestone.**

5. **Damage cooldown duration:** Long enough that the player can escape (≥0.5s), short enough to feel dangerous. **Recommendation: 0.75s — tune during feel milestone.**
